# NEXY_FARVIEW_100 — External Runtime Verification Procedure

## Identity

- Target: Minecraft Bedrock 26.45 ONLY
- Add-on: `NEXY_FARVIEW_100.mcaddon`
- Source of truth: the exact production-tree HEAD supplied with the package
- This procedure produces runtime evidence; source/build/CI evidence must remain separate.

## Required environment

- Minecraft Bedrock 26.45 exact
- A reproducible test world with cheats enabled only where the scenario requires them
- One primary client for single-player tests
- Two clients/devices for multiplayer tests
- Ability to capture chat/log output containing `NEXY_RUNTIME_EVIDENCE`
- For performance: FPS counter or profiler, TPS/tick timing where available, OS memory/CPU/thermal telemetry

## Baseline capture

1. Record the add-on package SHA-256.
2. Record the repository production HEAD used to build the package.
3. Record Bedrock version shown by the client/server.
4. Record device model, OS version, RAM, graphics mode and configured render distance.
5. Start a fresh test world and record baseline performance for 60 seconds.

## A. Add-on load / API binding

1. Import the exact package.
2. Activate the behavior pack in a fresh world.
3. Join with one player.
4. Capture `NEXY_RUNTIME_EVIDENCE` from the first spawn.

PASS requires:
- pack loads without script error;
- `system.run+clearRun` reports PASS;
- view-direction capability reports PASS;
- every capability being claimed for the scenario reports PASS.

FAIL criteria:
- pack does not load;
- script error;
- required capability reports FAIL.

## B. Gameplay event wiring

Perform one controlled instance of each:

- movement/input;
- camera rotation;
- melee hit;
- hurt event;
- projectile hit entity;
- projectile hit block;
- block break;
- block place;
- block interaction;
- inventory item change;
- item use;
- entity death;
- lever/pressure-plate/piston activity.

PASS requires the corresponding runtime instrumentation to record the expected gameplay class and no unrelated gameplay failure.

## C. Combat targeting / obstruction

Prepare three entities in one dimension:

1. target directly in front within range;
2. nearer entity with requested target behind it;
3. solid block between attacker and target.

Execute one attack per case.

Expected:
- direct first target: accepted path may proceed to runtime-controlled damage handling;
- nearer entity: requested target is rejected;
- obstructed target: attack is rejected.

Capture target identity, distance, obstruction state, result reason and any runtime error.

## D. Damage / cooldown / critical / armor / resistance

Use controlled entities and record health before/after each isolated attack.

Cases:

1. normal base damage;
2. critical-eligible attack;
3. armor present;
4. resistance present;
5. stacked modifier case;
6. second attack before cooldown expiry;
7. attack after cooldown expiry.

Expected pipeline:

`target -> critical -> armor -> resistance -> modifiers -> final -> engine damage`

Do not mix cases when measuring numerical outputs.

## E. Knockback / effect / durability

For each successful controlled combat case:

- capture target position/velocity before and after;
- capture effect IDs/duration/amplifier;
- capture main-hand item durability before and after.

PASS requires the observed result to match the request and runtime implementation for that exact case.

## F. Projectile

Test:

- projectile hits entity;
- projectile hits block;
- same projectile event delivered twice;
- distinct projectiles against the same target.

Expected duplicate handling:
- duplicate event is rejected by deduplication;
- no duplicated combat side effect is observed.

## G. Death / loot / XP

Use a disposable test mob with a known loot table and XP behavior.

1. Record target health.
2. Perform controlled lethal damage.
3. Observe death event.
4. Observe loot drops.
5. Observe XP changes.

Each observation is independent evidence. Death event observation does not by itself prove loot/XP correctness.

## H. Far-view 100 semantic test

Record these independently:

1. logical target count generated by the add-on;
2. engine-loaded chunk count if measurable;
3. client-rendered chunk count if measurable.

Never combine these into one number.

The repository's logical target contract expects 100 unique targets. A client-rendered result requires independent client evidence.

## I. Performance scenarios

Measure at least 60 seconds each:

1. idle;
2. normal movement;
3. combat;
4. 100 logical far-view targets active;
5. burst movement/camera movement;
6. sustained 10-minute run;
7. two-player multiplayer.

Capture:

- FPS;
- TPS or equivalent tick timing;
- script tick duration;
- CPU;
- memory;
- thermal state;
- queue size;
- executed task count;
- tracked chunk count;
- projectile dedup counts.

No metric may be inferred from source code.

## J. Multiplayer

Two players in the same world:

1. move independently;
2. fight the same target;
3. fire projectiles concurrently;
4. move through far-view workload boundaries;
5. repeat attacks rapidly.

PASS requires synchronized state, no duplicated damage, no missing critical gameplay events and no player starvation attributable to far-view work.

## K. Java parity

For every behavior claimed as Java-like:

`JAVA REFERENCE CASE -> EXPECTED RESULT -> BEDROCK OBSERVED RESULT -> DIFFERENCE/JUSTIFICATION`

At minimum test:

- hit targeting;
- obstruction;
- cooldown;
- critical;
- armor/protection;
- resistance;
- modifiers;
- knockback;
- durability;
- projectile;
- death;
- loot;
- XP.

No structural similarity or function naming counts as parity proof.

## Evidence record

For every scenario record:

- test ID;
- exact Bedrock version;
- package SHA-256;
- repository HEAD;
- device/client identity;
- scenario setup;
- exact action sequence;
- expected result;
- observed result;
- telemetry;
- logs/screenshots/video where applicable;
- PASS / FAIL / NOT VERIFIED;
- operator/date.

## Failure rule

Any contradiction, runtime exception, duplicated side effect, incorrect numerical result, starvation, unexpected memory growth, or mismatch with the locked specification invalidates PASS for the affected requirement until repaired and re-tested.
